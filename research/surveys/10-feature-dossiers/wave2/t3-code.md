# T3 Code — Feature Dossier
Registry: #50 | Category: 01 | Verified: 20,248★, MIT, last push 2026-08-24 (repo-verify.txt 2026-08-24)

pingdotgg's "agent harness control surface": a local backend that drives coding agents already installed on your machine (Claude Code, Codex, Cursor, Grok Build, OpenCode), with iOS/Android apps, a hosted web app, and an Electron desktop app as remote views. Execution stays on the owner's machine — the litmus passes — but what it controls are vendor harness CLIs, which LastHarness excludes; its transport/auth/approval design is the payload.

## Feature inventory
- Control surface for local agents: works with subscriptions on Claude Code, Codex, Cursor, Grok Build, and OpenCode "if they're set up on your computer"; backend + local web UI launched via `npx t3@latest` (Node ≥22.16); desktop app via winget/brew/AUR [VERIFIED-fetched:https://raw.githubusercontent.com/pingdotgg/t3code/main/README.md]
- Pairing protocol: `t3 pair` mints a one-time pairing token + QR code against a running server without restart (honoring `~/.t3` shared install or worktree dev server); device exchanges token → server creates an authenticated session; subsequent access is session-based, no long-lived secret on the device [VERIFIED-fetched:https://raw.githubusercontent.com/pingdotgg/t3code/main/docs/user/remote-access.md]
- Session/credential lifecycle management: `t3 auth` issues additional pairing credentials, inspects active sessions, revokes old pairing links or sessions; T3 Connect environments can be deregistered account-side even if the server is wiped [VERIFIED-fetched:https://raw.githubusercontent.com/pingdotgg/t3code/main/docs/user/remote-access.md]
- Transport ladder: loopback default; LAN HTTP endpoints; `t3 serve --tailscale-serve` publishes HTTPS via Tailscale Serve on a MagicDNS URL (`--tailscale-serve-port`, `--ttl`, `--base-dir` flags); desktop-managed SSH launch probes the host, starts/reuses a remote server, opens a LOCAL port forward so the renderer talks to a forwarded endpoint while the remote host owns projects/files/git/terminals/provider sessions [VERIFIED-fetched:https://raw.githubusercontent.com/pingdotgg/t3code/main/docs/user/remote-access.md]
- Hosted web app pairing without proxying: `https://app.t3.codes/pair?host=...#token=PAIRCODE` — browser connects DIRECTLY to the owner's backend; credential lives in the URL hash fragment so it is never sent to the hosted app server; explicit guidance NOT to use hosted pairing over plain HTTP (mixed-content rules) [VERIFIED-fetched:https://raw.githubusercontent.com/pingdotgg/t3code/main/docs/user/remote-access.md]
- Security posture notes: treat pairing URLs/tokens like passwords; prefer binding to tailnet/private addresses over exposure; documented risk that anyone with a valid pairing credential can create sessions until expiry/revocation; recommended setup is a trusted private mesh network for stable address + network-layer transport security [VERIFIED-fetched:https://raw.githubusercontent.com/pingdotgg/t3code/main/docs/user/remote-access.md]
- Per-thread permission modes: Supervised (ask before commands AND file changes; work outside workspace restricted), Auto-accept edits (edits auto-approved, commands still ask), Auto (routine proceeds, risky asks — Codex delegates to AI reviewer, Claude uses its own auto mode, others fall back to asking), Full access (default; unattended until done) [VERIFIED-fetched:https://raw.githubusercontent.com/pingdotgg/t3code/main/docs/user/permission-modes.md]
- Remote approval flow: approvals appear inline in the conversation from any paired client (phone included) — approve/reject one and the agent continues; mobile offers the same four modes with same labels; mode set per thread, child threads inherit [VERIFIED-fetched:https://raw.githubusercontent.com/pingdotgg/t3code/main/docs/user/permission-modes.md]
- Provider-native translation of modes: each provider maps modes onto its own approval policy and sandbox level (e.g. Supervised = prompting enabled + restricted workspace; Full access = both disabled); exact translation internal/changeable [VERIFIED-fetched:https://raw.githubusercontent.com/pingdotgg/t3code/main/docs/user/permission-modes.md]
- Ops surface: version-sync warnings between app and remote server with guided update/reconnect; Linux background-service docs keeping server alive after logout; multiple accounts per provider (Codex/Claude); source-control integrations; project icons/keybindings customization [VERIFIED-fetched:https://raw.githubusercontent.com/pingdotgg/t3code/main/README.md]

## Notable absences
No audit log of approvals (who approved what, when, from which device — inline approvals vanish into conversation history; nothing indicates persistence to an immutable record). No end-to-end encryption claim beyond "transport security at the network layer" — a plain HTTP LAN pairing path exists with only convention discouraging it. No per-tool/per-command allow-list granularity below the four coarse modes (delegates real restriction to each provider CLI's native settings). Hosted web app is third-party-served JavaScript with no self-host bundle offered yet ("very very early", big features not accepted). No multi-owner model anywhere — fine for LastHarness, but no delegation/least-privilege story either.
