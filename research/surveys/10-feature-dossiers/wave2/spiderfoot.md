# SpiderFoot (smicallef/spiderfoot) — Feature Dossier
Registry: #122 | Category: 03 | Verified: 21,383 stars, MIT, last push 2026-04-13

## Feature inventory
- **OSINT automation over a 200+ module publisher/subscriber feed graph**: "SpiderFoot's 200+ modules feed each other in a publisher/subscriber model to ensure maximum data extraction"; scan targets span IP address, domain/sub-domain, hostname, network subnet (CIDR), ASN, e-mail address, phone number, username, person's name, bitcoin address; most modules need no API key and many keyed ones have free tiers [VERIFIED-fetched:https://raw.githubusercontent.com/smicallef/spiderfoot/master/README.md]
- **Module catalog typed by provenance**: every module in the catalog carries a type label — Internal / Free API / Tiered API / Commercial API / Tool (Tool = wraps a locally installed Nmap, Nuclei, TruffleHog, testssl.sh, DNSTwist, WhatWeb, CMSeeK, WAFW00F, Retire.js, snallygaster, onesixtyone, nbtscan) [VERIFIED-fetched:https://raw.githubusercontent.com/smicallef/spiderfoot/master/README.md]
- **YAML-configurable correlation engine (v4.0)** with 37 pre-defined rules shipped in `/correlations`; the defining constraint: "correlation rules analyze scan data, they don't collect data from targets" — deterministic post-hoc analysis over already-collected events [VERIFIED-fetched:https://raw.githubusercontent.com/smicallef/spiderfoot/master/correlations/README.md]
- **Correlation rule schema (special attention)**: `id` (must equal filename) / `version` / `meta` (`name`, `description`, `risk` constrained to `INFO|LOW|MEDIUM|HIGH`) → `collections` (one or more `collect` blocks; the first `method` pulls from the database, subsequent `method`s refine; methods `exact`|`regex` over fields `type`|`module`|`data`, with `source.`/`child.`/`entity.` lineage prefixes referencing the discovery path of each element) → optional `aggregation` (bucket by field) → optional `analysis` (`threshold` with minimum/maximum/count_unique_only, `outlier` with maximum_percent/noisy_percent, `first_collection_only`, `match_all_to_first_collection` with contains/exact/subnet) → `headline` with `{field}` interpolation and optional `publish_collections` [VERIFIED-fetched:https://raw.githubusercontent.com/smicallef/spiderfoot/master/correlations/README.md]
- **Rules compile to SQL + Python over SQLite**: "SpiderFoot translates the YAML rules into a combination queries against the backend database of scan results and Python logic"; correlation results persist in `tbl_scan_correlation_results` with `tbl_scan_correlation_results_events` mapping result↔evidence-events, both directly queryable [VERIFIED-fetched:https://raw.githubusercontent.com/smicallef/spiderfoot/master/correlations/README.md]
- **SQLite back-end for custom querying**, CSV/JSON/GEXF export, embedded web-server UI or full CLI operation, Python 3.7+, Dockerfile provided [VERIFIED-fetched:https://raw.githubusercontent.com/smicallef/spiderfoot/master/README.md]
- **TOR integration for dark web searching** [VERIFIED-fetched:https://raw.githubusercontent.com/smicallef/spiderfoot/master/README.md]
- **Commercial HX tier is "100% Cloud-based and managed"**: attack-surface monitoring with change notifications via email/REST/Slack, multiple targets, multi-user collaboration, 2FA, Splunk/ElasticSearch/REST feeds [VERIFIED-fetched:https://raw.githubusercontent.com/smicallef/spiderfoot/master/README.md]

## Per-feature verdict
| Feature | Type | LastHarness landing | Rationale |
|---|---|---|---|
| YAML correlation rule schema (collections → aggregation → analysis → typed-risk headline) | 🧩 | §14.7 incident_log rule-format candidate | The special-attention finding: a declarative match-condition DSL whose output is a typed `risk` level plus a templated headline is exactly an incident-rule format. Lineage prefixes (`source.`/`child.`/`entity.`) preserve evidence chains per finding, and rules compile to plain SQL over an event table — directly portable to LastHarness's SQLite decision log as `incident_rules/*.yaml`. |
| Analysis operator set (threshold / outlier / first_collection_only / match_all_to_first_collection) | 🧩 | §14.7 detection semantics | Multi-source corroboration thresholds, noisy-percent outlier suppression, and found-here-but-not-there matching are the noise-control semantics an incident triage rule needs; each operator has defined options, i.e. an implementable spec, not a sketch. |
| Rules persist results as SQLite rows with an event-mapping table | 🧩 | §12 decision-log philosophy | Findings land as append-style rows traceable to their constituent events — the same auditable-replay shape LastHarness requires of the decision log. |
| 200+ module publisher/subscriber collection graph | 🧩 | §14.3 ingest hygiene | Deterministic feed-graph where each producer's output becomes another consumer's input is the right shape for chained ingest; adopt the topology, not the fleet. |
| Provenance-typed module catalog (Internal/Free/Tiered/Commercial/Tool) | ⚙ | Security dept, §14.3 | Per-source capability disclosure lets a scan plan around what keys/sources an install actually has — same startup-disclosure move as dispatch-context capability lists. |
| 200-module egress fleet (hundreds of third-party lookup APIs, port scanning, banner grabbing) | ❌ | — | Execution reaches hundreds of external endpoints with no allow-list; adoptable only module-by-module as individually allow-listed §7.1 gateway connectors, which is a rebuild, not a deploy. |
| TOR integration for dark web search | ❌ | — | TOR's purpose is unattributable egress; incompatible with a logged, default-deny gateway where every exit is accountable. |
| Local tool wrapping (Nmap/Nuclei/TruffleHog/testssl.sh invoked as subprocesses) | ⚙ | Security dept via §16.6 | Calling vetted local scanners under deny-by-default allow-lists is precisely LastHarness's dispatch model; these become allow-listed worker tools. |
| Embedded web-server UI + CLI dual operation | ⚙ | §16.10 Owner Surfaces | Scan-configuration and findings-review console is a workable shape for the owner-facing security view. |
| SpiderFoot HX cloud tier | ❌ | — | "100% Cloud-based and managed" — execution happens on vendor infrastructure; litmus fails outright. |

## Notable absences
No authentication or multi-user support in the open-source edition (HX-only); no scheduling, persistent monitoring, or change notification outside HX; no REST API documented for the OSS version; no ML/LLM scoring anywhere — all analysis is deterministic YAML/SQL, which cuts both ways (auditable, but no semantic correlation); risk levels are a fixed four-value enum with no weighting or escalation policy between levels; rules are single-scan scoped with no cross-scan trend detection; upstream activity is the slowest of this batch (pushed 2026-04-13).
