# YC QM (yc-software/qm) — Feature Dossier
Registry: #88 | Category: 06 | Verified: 14,144 stars, MIT, last push 2026-08-22 (GitHub API 2026-08-24)

Skip-confirmation dossier. Recorded disposition: multiplayer boards redundant under single-owner kernel. **Confirmed** — and the repo confirms what it actually does: QM is a *multiplayer agent harness for work*, deployed to Slack and the web, whose entire premise is many employees each getting isolated personal workspaces plus shared channels/projects. Every load-bearing feature (per-person scoped memory/files/keychain/permissions, identity carrying between Slack and web, admin org config) exists to mediate multi-human collaboration — which collapses to dead weight under LastHarness's single-owner kernel. Deployment targets the operator's own Fly.io/AWS cloud accounts, failing the ONE-self-hosted-Linux-env litmus outright. [VERIFIED-fetched:https://raw.githubusercontent.com/yc-software/qm/main/README.md]

## Feature inventory
- Multiplayer harness shape: each person/room gets its own scoped memory, files, keychain view, permissions, crons, web apps, and durable sandbox; personal + shared scopes; same identity across Slack and web app [VERIFIED-fetched:https://raw.githubusercontent.com/yc-software/qm/main/README.md]
- Architecture: headless core (API · identity · policy · scheduler) wrapping an agent loop that drives swappable harnesses (Pi, OpenCode, Codex, Claude Code) against a small fixed tool surface — one tool, `execute`, runs commands in a per-scope durable sandbox; Postgres holds sessions/memory/queue; web UI/admin/portal are optional plugins over the core HTTP API [VERIFIED-fetched:https://raw.githubusercontent.com/yc-software/qm/main/README.md]
- Security postures chosen at org level, narrower scopes may only tighten: **Strict** (human approval per tool call), **Auto** default (classifier screens provenance-labelled external data and tool results before they reach the model), **Dangerous** (no screening/pauses) — with a predeclared command policy of approval rules and hard denials (recursive deletes, destructive SQL) applying in *every* posture [VERIFIED-fetched:https://raw.githubusercontent.com/yc-software/qm/main/README.md]
- Shared skills model: skills are scope-owned, shareable by grant, promoted org-wide only through an admin gate, and importable as skill packs from git repositories [VERIFIED-fetched:https://raw.githubusercontent.com/yc-software/qm/main/README.md]
- Deployment-directory contract: all org specifics live in `deploy/layers/<org>/` while core stays byte-identical upstream; private-fork pattern maintained by `update-qm`/`upstream-pr` boundary skills (nothing under deploy/layers travels upstream); contributions accepted as human-written prose in `adrs/`, not code [VERIFIED-fetched:https://raw.githubusercontent.com/yc-software/qm/main/README.md]

## Notable absences
No single-owner or local-first mode anywhere — cloud deployment via `qm init --target fly-or-aws` is the only path. No immutable audit ledger (auditing exists but rides the mutable Postgres layer). No non-technical solo-owner onboarding; assumes an org admin choosing postures. Harness-swappability is real but irrelevant if the substrate itself conflicts.
