# OpenClaw — Feature Dossier
Registry: #83 | Category: 07 | Verified: 387,325 stars, MIT per README badge (LICENSE file classified "Other"/NOASSERTION by GitHub API), pushed 2026-08-24 (GitHub API 2026-08-24)

Note-tier dossier. Recorded disposition: messenger delivery gateway shape post-V1 → §16.4 adapter design-note; ex-Clawdbot lineage confirmed in-repo ("Warelay -> Clawdbot -> Moltbot -> OpenClaw", VISION.md). The channel-gateway architecture in detail: **one long-lived Gateway daemon per host owns every messaging surface** — WhatsApp via Baileys, Telegram via grammY, Slack, Discord, Signal, iMessage, Google Chat, WebChat — and is the only component permitted to open those provider sessions (invariant: exactly one Baileys session per host). Control-plane clients (macOS app, CLI, web UI) and device **Nodes** all connect to the Gateway over WebSocket (default bind `127.0.0.1:18789`) using a typed protocol: mandatory first `connect` frame, `req`/`res`/`event` JSON frames validated against JSON Schema, discovery metadata in `hello-ok`, **idempotency keys on side-effecting methods (`send`, `agent`) with a server-side dedupe cache**, and events explicitly *not replayed* (clients refresh from snapshots). Trust is pairing-based: every client presents a device identity, new devices require explicit approval and receive a device token, connects sign a challenge nonce (v3 binds platform/deviceFamily), loopback auto-approves, everything non-local requires approval.

## Feature inventory
- Single-operator personal assistant running on your own devices; models, tools, messaging channels, and companion apps connected through **one Gateway** [VERIFIED-fetched:https://raw.githubusercontent.com/openclaw/openclaw/main/README.md]
- Gateway = local control plane for sessions, tools, events, and channel connections; WS default `127.0.0.1:18789`; one Gateway per host is an invariant [VERIFIED-fetched:https://docs.openclaw.ai/concepts/architecture]
- Channel set: WhatsApp (Baileys), Telegram (grammY), Slack, Discord, Signal, iMessage, WebChat (+ Google Chat per README); the Gateway is the only place that opens a WhatsApp session [VERIFIED-fetched:https://docs.openclaw.ai/concepts/architecture]
- Typed WS wire protocol: mandatory connect handshake (hard close otherwise), req/res/event frames, JSON Schema validation of inbound frames, event types incl. `agent`/`chat`/`presence`/`health`/`heartbeat`/`cron`, idempotency keys + short-lived dedupe cache for `send`/`agent`, events never replayed [VERIFIED-fetched:https://docs.openclaw.ai/concepts/architecture]
- Pairing and local trust: device identity on connect, pairing approval → device token, signed `connect.challenge` nonce (v3 payload binds platform/deviceFamily), repair-pairing on metadata change, loopback auto-approve, non-local requires explicit approval; auth modes incl. Tailscale identity and trusted-proxy [VERIFIED-fetched:https://docs.openclaw.ai/concepts/architecture]
- Nodes: companion devices (macOS/iOS/Android/headless) connect with `role: node` declaring caps/commands — e.g. `camera.*`, `screen.record`, `location.get` [VERIFIED-fetched:https://docs.openclaw.ai/concepts/architecture]
- Inbound-untrusted default: "Treat inbound messages as untrusted input"; DM-capable channels pair unknown senders by default with `openclaw pairing approve <channel> <code>`; tools run on the host unless sandboxing is configured [VERIFIED-fetched:https://raw.githubusercontent.com/openclaw/openclaw/main/README.md]
- Works with hosted **and local** model providers [VERIFIED-fetched:https://raw.githubusercontent.com/openclaw/openclaw/main/README.md]
- Extensibility: tools/skills/plugins with a plugin SDK; two plugin styles (code plugins vs bundle-style packaging skills/MCP servers); ClawHub as the discovery/provenance/security-review marketplace; **memory is a special plugin slot with only one memory plugin active at a time**; MCP supported both as server and runtime surface [VERIFIED-fetched:https://raw.githubusercontent.com/openclaw/openclaw/main/VISION.md]
- Terminal-first onboarding by design — "we do not want convenience wrappers that hide critical security decisions" ; no usage analytics/tracking unless operator opts in [VERIFIED-fetched:https://raw.githubusercontent.com/openclaw/openclaw/main/VISION.md]
- Lineage: evolved through Warelay → **Clawdbot** → Moltbot → OpenClaw; developed by the OpenClaw Foundation non-profit (Steinberger et al.) [VERIFIED-fetched:https://raw.githubusercontent.com/openclaw/openclaw/main/VISION.md]

## Notable absences
No immutable audit trail: events are not replayed and no durable action-history store is documented at the Gateway level — LastHarness's SQLite decision log must wrap anything built on this shape. No multi-user/department concept (single operator by explicit design), so scoping beyond sender-pairing is absent. Host-run tools by default is the opposite of worker isolation; sandboxing exists but is opt-in configuration, not architecture. No egress policy engine — channel credentials live with the Gateway and any outbound call it can make is governed by config, not deny-by-default rules.
