This dossier details VoltAgent's agent-observability model — what the deferred visualization would actually consume and render.

## Feature inventory
- **Two-part platform**: an open-source TypeScript framework (`@voltagent/core`: agents with typed roles/tools/memory/model providers, declarative workflow engine, supervisors & sub-agents with task routing, Zod-typed tool registry + MCP, memory adapters, resumable streaming, RAG, voice, guardrails, evals) plus **VoltOps Console** for observability/automation/deployment, offered `Cloud` AND `Self-Hosted` [VERIFIED-fetched:https://raw.githubusercontent.com/VoltAgent/voltagent/main/README.md]
- **Observability model (the note-tier subject)**: VoltOps renders "real-time execution traces, performance metrics, and visual dashboards"; named surfaces are Observability & Tracing (deep-dive into "agent execution flow"), Dashboard (all agents/workflows/system metrics), Logs (per-interaction, per-workflow-step), Memory Management (inspect/manage agent memory, context, conversation history), Traces ("complete execution traces to understand agent behavior and optimize performance"), plus Monitoring (health/performance/resource usage) [VERIFIED-fetched:https://raw.githubusercontent.com/VoltAgent/voltagent/main/README.md]
- **Dispatch tree is first-class UI**: supervisor/sub-agent teams are a core framework concept ("teams of specialized agents under a supervisor runtime that routes tasks and keeps them in sync"), so traces naturally form a supervisor→sub-agent tree; the console's trace views are the visualization layer over that hierarchy [VERIFIED-fetched:https://raw.githubusercontent.com/VoltAgent/voltagent/main/README.md]
- **Human-in-the-loop workflow suspend/resume**: workflow chains suspend mid-step ("Manager approval required") with typed resume payloads, runnable and steppable from the console [VERIFIED-fetched:https://raw.githubusercontent.com/VoltAgent/voltagent/main/README.md]
- **Local dev server + cloud console pairing**: `npm create voltagent-app` boots an HTTP server on localhost:3141 whose startup banner links to console.voltagent.dev — local execution, hosted observation by default [VERIFIED-fetched:https://raw.githubusercontent.com/VoltAgent/voltagent/main/README.md]
- **Managed RAG service**: "VoltAgent Knowledge Base" for document ingestion/chunking/embeddings/search as a managed service [VERIFIED-fetched:https://raw.githubusercontent.com/VoltAgent/voltagent/main/README.md]
- **Console-side prompt builder, triggers & actions (webhooks/schedules), guardrails config, eval suites** — all operated from the VoltOps platform rather than in code [VERIFIED-fetched:https://raw.githubusercontent.com/VoltAgent/voltagent/main/README.md]

## Notable absences
No documented on-prem-only posture for the console data path at README level — even the self-hosted VoltOps tier is presented as a deployable platform, not a library the host app embeds; there is no stated file-local trace export format that would let LastHarness reuse its renderer without the platform. No policy enforcement story beyond guardrails-as-config: allow-lists, audit logs, or immutable records are absent from the primary source. License is MIT but the console platform's feature split (what is in the OSS repo vs the VoltOps product) is not delineated in the README. Nothing here changes the recorded disposition — the dossier's output is the §16.6/§12.4 design-note vocabulary (span nesting → tree render) and a confirmation that visualization is presentation-over-spans, deferrable without loss.
