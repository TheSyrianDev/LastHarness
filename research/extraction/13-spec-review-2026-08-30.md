## B. Fixed in this pass (commit `b0f1be8`)

**B1 — M0 contradicted three sections. *Blocker.***
§4.3, §5.4, and §17.2 each state that "Kernel, Memory (Information), and Security are always present" and are non-deselectable. §12.6 Layer 1 says the sanitization gate "runs inside the Information department." But M0 shipped Development alone, with Information absent until §16.3 item 10 — so M0's decision-log write path depended on a department that did not exist.
Fixed three ways: an explicit *milestones, not configurations* note (the always-present rule governs a shipped installation, not build order); the gate named as a direct kernel call at M0, migrating into Information at M1; and Information made the M1 second department — principled rather than arbitrary, since it is non-deselectable, hosts the §12.6 gate, and owns the memory handle.

**B2 — Arithmetic error.** Item 10 said "the remaining four departments" then listed five. Six − Development − Information = four. Now stated explicitly.

**B3 — Circularity between blocked item and gate.** Item 11 marks the evolution sandbox blocked on the undefined verification suite, but §16.8 Step 4 routes *every* department's going-live validation through that same sandbox. So item 10's "gated per §16.8" was gated by an undefined noun three items later. Now stated in item 11.

**B4 — Blank-evidence contradiction, introduced by tonight's merge.** §16.6.B.2's table said "Do not write" while §12.2.A said "Auto-write when only completion evidence exists," and §16.6.B.2's own next paragraph said workers "produce minimal decision-log entries." Resolved: the tier suppresses the *quality claim*, not the row.

**B5 — Two stale terms.** §16.10.2's Class A row still said "**V1.**" after §16.3 stopped using the term. §16.3 item 12 permitted "a cloud endpoint" during M0–M2, colliding with §16.1's unconditional kernel locality — now local `llama-swap` by default, cloud permitted for department/agent inference only.

## C. Open findings

Ranked by how much they'd bite a builder.

### C1 — "Verification suite" is still undefined. *Blocker.*
§11.3 step 3: *"Run full verification suite."* The document never says what is in it, who writes it, or what a PASS means. Blast radius:

- §11.3 evolution sandbox (§16.3 item 11, marked blocked)
- §16.8 Step 4 — **every** department's going-live gate, so all of item 10
- §10.2: *"only promoted… if it passed its verification suite"*
- §14.1 kernel self-update step 2: *"run the full verification suite"*
- Every sandbox assertion now in the spec: §4.5, §4.6, §7.1.B, §14.2, §14.5.A, §16.10.5

Four sections added tonight lean on it. **This is the highest-value open spec question** — it blocks department rollout, not just the sandbox.

### C2 — `commit_sha` has no producer. *Should-fix.*
§16.6.B.1's canonical success schema is `success: { commit_sha: str, … }`. But §16.6 Output 2 makes *"the worktree's `git diff`"* canonical, and §14.2's `merge_coordinator` is *"merge --no-ff --no-**commit** — no push, no tag, no remote mutation."* Nothing in the contract creates a commit, so `commit_sha` cannot be populated. Either the schema is wrong or a commit step is missing from the contract.

### C3 — Automation's scheduler has no defined tick. *Should-fix.*
§6.3: *"A routine job in the Automation department (§14.6) executes the retention policy."* §14.5.A needs periodic skill-freshness flagging. §14.7.A rules need periodic evaluation. All three need something to fire them. But §16.5 forbids resident agents, Automation itself is §16.3 item 10, and no §16.3 item covers the scheduler. A shipped system needs a cron-like tick that §16.5 currently appears to forbid.

### C4 — "Tool Profile" is cited but never defined. *Should-fix.*
§16.7: *"Both are Tool-Profile-gated (§8.2) capabilities."* §8.2's ACL table has only *"Tools | Whitelist of allowed tools per role."* The capitalized construct is referenced in at least three places with no schema or definition behind it.

### C5 — `agent-browser` runs as a resident daemon. *Should-fix.*
§16.7 runs it *"as its native MCP server,"* justified parenthetically as *"(pure Rust daemon)."* §16.10.4 states: *"**Explicitly excluded:** no standing daemons or listener processes (§16.5)."* §16.1 grants residency to `llama-server` via an explicit trust argument that is never generalized to third-party processes. Either `agent-browser` is per-dispatch (and the text should say so) or it needs a named §16.5 exception.

### C6 — §16.4 and §16.1 disagree on the installer call mechanism. *Should-fix.*
§16.4 strikes it resolved: *"~~**`installer/` call mechanism**~~ — In-process Python import."*
§16.1 still says: *"The exact call mechanism between the kernel and `installer/` … is not yet pinned down — resolve before implementation starts."*
One of these is wrong, and §16.1's version is the one that reads as an open blocker.

### C7 — §16.4's open-item count self-contradicts. *Nit.*
§16.4: *"Five of six are closed; one has two verification items still open."* It then lists a SaaS item as *"**stays unclosed** but unadopted"* in addition to the container-runtime item — two unclosed, not one.

### C8 — §8.2's standing-exception list is incomplete. *Nit.*
§8.2: *"See §14.4 and §14.7 for the departments currently using this exception."* §14.5's `retention_auditor` also holds one: *"Read (cross-dept: metadata only — age/type/dept tags, never content)."*

### C9 — Smaller open markers. *Nits.*
- §16.6: *"(Default assumption, not extensively discussed — flag if a different disposition is wanted.)"* — worktree-preservation marker, never closed.
- Field naming: `parent_id` in §16.1/§16.6 vs `Previous ID` in §12.2/§12.3. Same field, two names.
- §1 has `### 1.2 Why This Matters` but no `1.1`.
- §16.1: *"Only one model is ever loaded at a time"* vs a manager session that dispatches workers and then writes the completion entry — the manager must stay live across a worker on a different model alias. Never reconciled.

## D. Recommendation

**Define the verification suite (C1) before writing M0 code.** It is the only blocker that gates other work: without it, §16.8 has no defined gate, so no department can legitimately move to `active`, and four sandbox assertions are untestable promises. It is a short section — what runs, what counts as a pass, who may extend it — and it unblocks more than anything else on this list.

C2–C6 are each a paragraph to fix, and C2 (`commit_sha`) should be settled before M0 because it sits directly on the dispatch contract's return path.

C7–C9 are cosmetic and can be swept whenever.
